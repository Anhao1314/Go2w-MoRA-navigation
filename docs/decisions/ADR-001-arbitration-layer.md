# ADR-001：主线改为可验证仲裁层的架构验证

- **状态**：接受
- **日期**：2026-10-23
- **相关**：[架构 v0.2](../ARCHITECTURE_V2.md)、[路线图](../ROADMAP.md)、[历史 MVP](../MVP.md)

## 背景

最初的计划是在 Isaac Lab 训练 Go2 速度跟踪策略，再做 Isaac → MuJoCo 跨引擎迁移并归因损失。调研 6 份足式 RL 岗位 JD 后发现：纯 RL 训练与跨引擎迁移在候选人中同质化严重；真正被反复要求的是**安全、可解释、可验证控制**以及**分层系统设计**。

同时，仓库已有 `mora/` 分层运行时与 `cpp/` 控制栈，但层间只有数据契约（`Goal` / `Action`），没有约束契约——S1 的输出直接进入 S0，安全性依赖训练分布与事后停机。

## 选项

1. **继续原 MVP**：三种子 + 跨引擎迁移归因。优点是方法成熟；缺点是差异化弱，且与"架构"能力无关。
2. **端到端 VLA**：硬件不足（16 GB 只能跑小模型），且与现有资产不匹配。
3. **可验证仲裁层**：在 S1 与 S0 之间加入 C++ 物理检查，研究干预率与性能损失的权衡。复用现有全部资产，且直接对应 JD 的安全/可验证控制要求。

## 决定

选择选项 3。主线目标改为：用 A/B/C 对照实验回答"可验证约束能否在不显著损失性能的前提下降低危险状态发生率"，并以 C++ 核心 + 运动物理学作为技术支撑。

## 后果

**正面**

- 差异化明确：从"会训模型"转为"能做架构与可验证性设计"。
- 负结果亦可交付：若性能损失过大，"约束的代价"本身是结论。
- 复用三种子基线、场景阶梯、冻结种子集、证据束与 CI。

**负面 / 风险**

- C++ 动力学实现与数值对齐需要额外时间（约 1 周）。
- 仲裁效果不确定，H1 可能不成立。
- 原 MVP 的跨引擎迁移降为可选（P3），若时间不足则不做。

**跟进**

- 需在 W2 末确认批量性能（< 1 ms / 2048 envs）；不达标则降采样并记录。
- RNID 为加分项，超时降级为 PD 力矩限幅。
